# 반동 궤적 재현: 게임 데이터로 정해지는 것과 추정인 것

2026-11-25 빌드PC, 게임 26568081. 게임은 켜지 않았고 데이터 표(`data/game/*.dl_bin`, 형식 정의 `dl_library.dl_typelib`)만 봤다. 칸 자리는 typelib, 칸 이름은 filediver datalibrary 구조체 순서로 맞췄다. 사이트 시뮬레이션 식은 분석PC 편지 `우편함\빌드PC행\20261125_1410_반동궤적_재현자료.md` 의 설명을 따랐다.
참고 구현은 `사이트용\ui\recoil-sim-ref.js`.

## 1. 사이트 추정 상수 4개의 결론

| 상수 | 결론 | 근거 |

정리: 궤적의 크기와 모양을 정하는 입력(반동 값, 배율, 치우침, 무작위 비율, 분당 발사, 탄창, 사격 방식, 자세와 방어구 배율)은 모두 게임 칸이다. 시간 축(한 발 반동이 얼마 동안 들어가고 돌아오는지)은 게임 코드(game.dll) 안이라 데이터에 없다.

## 2. 반동 단위

결론: **데이터로 정하지 못함.** 후보 둘.
- (가) 초당 각도(도/초): filediver 주석 "Defined in degrees / second". 근거는 주석뿐이고, typelib 형식은 이름 없는 FP32 라 단위 정보가 없다.
- (나) 한 발당 크기(사이트의 0.01 도/점): 화면 숫자(무기고 통계)가 이 값의 평균 그대로라 값 자체가 '한 발 크기' 꼴로 쓰인다(시트 README 의 `조작.화면`).
- 두 후보는 궤적으로 가르기 어렵다. 한 발 반동을 속도 v(도/초)로 넣고 시간 상수 τ 로 줄이면 한 발 이동량은 v × τ 이다. 그래서 '값 x UNIT' 과 '값 x τ' 는 같은 궤적을 낸다(UNIT = τ). 데이터로 정할 수 있는 것은 무기 사이의 비율뿐이고, 절대 크기는 화면 측정 없이는 정해지지 않는다.
- 같은 구조체 안의 각도 칸(3절 `칸8_12`, 값 90/85/80/60/45)은 도 단위가 분명하지만 반동 값과 크기 범위가 달라 단위 근거가 되지 않는다.

## 4. 찾아본 곳 (회복, 시간, 연사 누적, 탄퍼짐 증가와 회복, 자세 배율)

- WeaponDataComponent 79칸 전부(typelib 1240 B): 반동, 배율, 탄퍼짐 3칸(SpreadInfo 의 bool 은 모든 무기 0), 흔들림, 조준 배율, 사격 방식, 이름 없는 실수 칸(3절)
- RecoilInfo, RecoilComponentInfo, RecoilModifiers, SpreadInfo, SpreadModifiers: 칸 수가 filediver 와 같고 남는 칸 없음
- WeaponRoundsComponent(탄창 두 개의 반동, 탄퍼짐 배율), WeaponChargeComponent, WeaponHeatComponent, WeaponWindUpComponent(셋 다 filediver 구조체에 반동, 탄퍼짐, 흔들림 칸 없음), ProjectileWeaponComponent(발사 화면 흔들림 WeaponCameraShakeInfo 는 흔들림 자원 해시 3개 + 실수 2개로, 조준 방향이 아니라 화면 흔들림 효과)
- AvatarComponent 28칸(피로 단계, 조준과 사격 준비 시간): 반동 회복 칸 없음
- StanceComponent(자세 3개 x Vec2 8): 기록은 SEAF 병사 NPC 하나뿐, 헬다이버 자세 배율(0.9, 0.6, 0.4)이 아님
- 형식 이름 1,208개 중 이름을 아는 1,088개에서 recoil, sway, spread, aim, camera, stance, exertion, injury, wound 이 든 것 전부. 이름 모르는 120개는 보지 않았다(남은 빈틈)
- 결론: 시간 상수, 회복, 연사 누적, 탄퍼짐 증가와 회복, 자세 배율, 0.57 도 규칙, 1/16 규칙은 데이터 표에 없다(게임 코드 안). 게임 코드는 암호화되어 있어 보지 않았다(메모리 rea-ghidra-game-binary)

## 5. 식 (참고 구현과 같음)

한 발마다(간격 60 / 분당_발사 초, 최대 30발):
1. 탄착점 = 지금 화면 방향 + 지금 drift(탄이 나간 뒤 그 발의 반동이 걸림, 첫 발은 조준점)
2. 총반동(drift)과 카메라반동(climb) 각각: 수평 = 실효 수평 x clamp(치우침 + 가로 무작위 x U(-1,1), -1, 1), 수직 = 실효 수직 x (1 - 세로 무작위 x U(0,1)). 여기에 UNIT(추정)과 자세 배율 x 방어구 패시브 배율
3. 화면 수평이 한쪽으로 0.57 도를 넘었으면 가운데로 돌아오는 쪽 반동을 1/16 로(helldiversotl)
4. drift 는 축마다 지금 값과 새 반동 중 큰 쪽, climb 는 남은 반동을 새 반동으로 바꿔 침
5. 시간이 흐르면: drift x exp(-dt / DRIFT_TAU), 남은 climb 의 (1 - exp(-dt / CLIMB_TAU)) 만큼 화면에 더함. 화면은 돌아오지 않음
6. (후보) 화면, drift 를 `칸8_12` 각도 안으로 자름

## 6. 참고 구현의 입력 칸

`simulate(sim, scale)` 의 `sim` 은 사이트 weapon-recoil.js 꼴 그대로(`drift`, `climb`, `bias`, `random`, `rpm`, `magazine`). 더한 칸:
- `limit`: `[[총반동 칸8_12], [카메라반동 칸8_12]]`(시트 `조작.총반동.칸8_12`, `조작.카메라반동.칸8_12`). 없으면 90
- `climbBias`: 카메라반동 수평 치우침이 총반동과 다를 때(시트 `조작.카메라반동.수평_치우침`). 없으면 `bias`
- `scale` 에 방어구 패시브 배율을 곱해 넘김(예: 엎드려 0.4 x 공병 키트 0.7)
- 사격 방식이 점사면 `점사_발수` 발마다 끊어 그릴 수 있음. 점사 사이 쉬는 시간 칸은 데이터에 없음
